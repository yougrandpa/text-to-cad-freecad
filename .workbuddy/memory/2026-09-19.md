### 本轮揪出的 8 个缺陷（前 5 个是本轮引入或暴露，任何单测都不会发现）
1. `rpc.py` 用了未导入的 `E_COMPILE` —— `detail.get("kind") or E_COMPILE` 短路求值，只在"错误详情没有 kind"时爆。**把精确的 solver 错误替换成 NameError**，恰好摧毁可自修复性。

4. `base_version: "current"` 被拒 —— 最自然的写法换来无用的 pydantic 错误。→ 纳入工具契约。
5. `build_client` 接受空 `base_url` → **SDK 静默回退 `api.openai.com`**，提示词与 Key 发给了没选的厂商。→ 显式拒绝。
6. UI `$("viewPort")` vs HTML `viewport` → 静默 null。→ 加 id/class/资源引用的静态一致性测试。
7. `SessionDB` 硬绑单线程 → HTTP 线程池下第二个请求即崩。→ `check_same_thread` 参数 + RLock。
8. `context_window` 有默认值 → 无法区分"未设置"与"显式设成 128000"，预算阈值按错窗口标定。→ 改 Optional + `resolved_context_window()`。

**教训**：1/3/4/8 是"默认值或兜底逻辑让错误看起来像正常"；2/5/6/7 是"两个地方各写一遍同一个事实"。前者靠端到端跑出来，后者靠单一事实来源。

## 追加：「跑完了不知道完成」的根因（用户实测反馈）

用户配好 DeepSeek 后实测报："左边模型执行代码，中间不实时渲染，跑完也不知道完成了。" 查出**三个独立缺口**，前两个都是我的错：

### 1. 结论表用枚举名做键，永远匹配不到（直接原因）
`result.state` 从 SSE 来的是 pydantic 对 `(str, Enum)` 的序列化结果 —— **小写值** `"succeeded"`；而我的表键是 `SUCCEEDED`。**永远命中不了**，于是 turn 结束时屏幕上**根本没有结论**，唯一的信号是文字安静地停了。

更糟的是**测试放过了它**：旧测试只断言文件里出现过 "SUCCEEDED"/"EXHAUSTED" 这两个**字符串** —— 它们确实出现过，作为那些永远匹配不到的键。

→ 修：键改小写值；**新测试把表的键与 `TurnState` 本身对比**，两侧再也不可能漂移。同类检查适用于 `CheckStatus`/`Severity`（它们恰好是对的）。

### 2. 视图只在 turn 结束后刷新
engine 的 observer 早就在 tool 帧里带了 `images`，但前端**完全没读**。而且 `/render` 只在 handleResult 里调一次。

→ 修：tool 帧带图就立即显示（`applyToolImages` → `displayImage`），Gate 通过的 commit 也刷新视图（模型不主动看图时也有图）。为此服务端必须给图附**可访问的 URL**（engine 报的是磁盘绝对路径，浏览器用不了）。

**证据（帧时序）**：
```
13.6s  ir_commit  ok=True  gate=PASS
13.6s  geo_view   ok=True  images=['iso','top'] urls=[...?version=4]
13.6s  result     state=succeeded
```
两者都排在 `result` 之前 → 确实是过程中更新。

### 3. 进行中没有任何指示
一分钟的静止画面与"卡死"无法区分。→ 加 live 行：当前步骤 + 当前工具 + **已用时秒表**，并**钉在底部**（append 已有节点会移动它 —— 第一版就是被它描述的内容顶上去的）。

### 附带修掉的真 bug
**未知模型返回 500 而非 404**。根因值得记：
```python
def current_version(self, model_id):
    try: return int(self.ir_store.load(model_id).version)
    except FileNotFoundError: return 0     # ← "不存在" 与 "就是 v0" 同值
```
`create()` 造出来的模型**就是 v0**，所以它区分不了。render/artifacts 三个端点改为一律用 `load()` 取版本，并在该方法 docstring 里写明这个歧义。**症状出现在 UI（中间显示 Internal Server Error），根因在存储层的返回值语义。**

### 工具
- `tools/stub_llm.py` 新增 `--delay N`：模拟慢模型，否则 2 秒跑完，**UI 的进行中状态根本无法被观察或验证**。这是能测出来的前提。
- 验证实时性的办法：用 python 逐行读 SSE 并给每帧打时间戳，比截图可靠（脚本的 mid-turn 窗口只有几百毫秒，截不到）。

## 追加：真机首跑 DeepSeek —— 第 2 步就炸，暴露一个协议缺口

用户配好 key 后第一次真机跑（需求：「给这个立方体加两个手臂和两条腿」），第 2 步报：

```
400 The `reasoning_content` in the thinking mode must be passed back to the API.
```

**根因**：DeepSeek 思考模式返回的 assistant 消息带 `reasoning_content`，**同一轮内**多步循环回放时必须原样带回。而它**在进入系统的第一跳就丢了** —— `LlmReply` 没这个字段，`_parse` 也没读，engine 自然无从回显。

**一轮是多步循环 ⇒ 每步都在回放上一步的 assistant 消息 ⇒ 这个缺陷必然在第 2 步爆，且任何思考模型都会。**

**为什么 402 个离线测试全绿也没发现**：`stub_llm.py` 不产生 reasoning（它不是思考模型），这条要求只存在于真实协议里。与"只测成功路径"是同一类盲区——**只有真机能证明真机**。

**修复**（`client.py` + `engine.py`）：`_parse` 读 `reasoning_content`（回退 `reasoning`）；engine 构造 assistant 消息时**有则回显、无则不加键**（不给普通模型塞 `reasoning_content: null`）。

**修复后真机验证**（「60x40 底板厚 10mm」）：
```
 1.5s ir_get/ir_digest ok   6.1s ir_patch FAIL(invalid IR)   8.7s ir_patch ok
10.2s ir_patch ok          11.2s ir_commit gate=PASS
11.2s RESULT succeeded steps=5 tokens_in=21741 tokens_out=2568
```
**11 秒、5 步、Gate 全绿、几何正确**（60×40×10）。而且第 2 步的失败被**模型自己读懂并修正**（它自己指出 `refs` 的语义）——这是本项目最核心假设（反馈质量决定能否自修复）的第一次真机证据。

**新增** `tests/unit/test_llm_client.py`（这个模块此前一个测试都没有）。

## 追加：真机跑「加手臂和腿」—— 又暴露三个问题（其中一个是核心弱点）

用户报的下一个用例：「给这个立方体加两个手臂和两条腿」。

### 6. `reasoning_content` 必须回传（已在上节记录）
第 2 步 400，因为思考模式的 assistant 消息必须原样带回它的 reasoning。

### 7. **工具描述用通配写法，模型看不见已有能力**
IR 里**本来就有** `additive_box` / `additive_cylinder` / `subtractive_*`，worker 也实现了（`PartDesign::AdditiveBox`）。但我的描述写的是 `additive_*` —— 模型不知道这一族里有什么，于是用 `pad` 建了三个**互不接触**的实体 → Compound → `solid_count` 失败。
**13 步、178k token、失败。**

关键补充：**同一 body 内的特征只有在几何上真的相交时才合并**；`refs` **只声明构建顺序，不产生任何几何关系**（指向躯干并不会让手臂长在躯干上）。这条现在写进描述，并给出面附着写法 `plane: {kind:"face", feature_id:..., sub:"Face6"}`。

**改完后同样的需求：5 步、35k token、一次 patch、Gate 全绿。**

### 8. **核心弱点：Gate 全绿 ≠ 需求满足**
模型建了"两根校准探针"就 commit，Gate **PASS**，turn 结束 —— 没有手臂也没有腿。
原因：**它没有把用户的要求转成 confirmed 的 ConstraintExpr**，而 `bbox_spec`/`mass_spec` 在**没有对应需求时返回 PASS**（"no confirmed bbox requirement"）——**没做任何校验却报通过**。

这是本项目最危险的一类错误：**假绿**。

**修复**（不改变「全绿=完成」这条不变量）：
- `bbox_spec`/`mass_spec` 无需求时改报 **SKIP**（进 `skipped_checks`，可被看见）
- 新增 advisory 检查 **`requirement_coverage`**：无 confirmed 约束时明确说"只验证了几何自洽，没有验证是否符合要求"
- `ir_commit` 的 PASS 文案不再只说 "Build succeeded"，而是说明它**没有**判过任何需求
- 工具描述里把 `update_requirement` 标成 "THE ONLY THING THE GATE JUDGES AGAINST"

fail-closed 语义未动（全 blocking SKIP 仍为不通过）。

### 教训
**"通过"这个词必须精确到"证明了什么"。** 一个 check 在无事可做时返回 PASS，比返回 FAIL 危险得多 —— 后者会被看见，前者会被信任。

## 取消预算上限（用户指令：「不要设置预算上限」）

### 语义选择
`None` = 不设上限（**不是** 0，也不是大数）。理由：`0`/`999999` 作为「无限」是在不同方向上静默出错的约定，
`None` 说它自己的意思，且 `is None` 不会被算术搞错。`0` 仍是**真上限**，有专门测试守着这条区别。

五项默认全为 `null`（`configs/default.yaml`）。此时一个 Turn 只会在三件事上结束：
Gate 全绿 / `FAILED` / `AWAITING_APPROVAL`。

### 关键区分（写给下一个改这块的人）
取消**工作量上限**不影响**单次请求活性**：挂死的 LLM 仍撞 `llm.request_timeout_s`、
挂死的工具仍撞 `ToolSpec.timeout_s`、死 worker 仍撞传输超时。前者是策略，后者是防卡死，**不要一起删**。

### 去掉上限的必然推论（本次一并修的）
1. **客户端断开必须终止 Turn** —— 以前靠 `max_steps_per_turn` 兜底，否则关掉页面会留下永久后台回合持续烧 token。
   实现里踩到：`yield start` 原本在 `try` **之前**，生成器在进入 try 前被关闭时 `finally` 不执行 → 清理失效、任务泄漏。
2. **顺手修掉 tap 累积** —— 每次 `/chat` 都把 `services.hooks` 包一层 `HookEventTap` 且不还原，长跑服务会逐请求累积。
3. **无上限必须可见** —— `/health` 报 `budget.*`，界面顶栏加「无预算上限」徽标。静默的宽松设置会让人用「跑了很久没结束」去推断它。

### 反证实测（真实路径，非单测）
生成 `tools/sessions/long_run.json`（22 个校准步 + 4 步底板建模 = 27 步，旧上限 24）：

| 配置 | 结果 |
|---|---|
| 默认（无上限） | `succeeded` **26 步**，Gate 全绿 |
| `strict.yaml` 有界档 | `exhausted` 第 **12** 步，`budget exhausted: max_steps_per_turn (limit=12)` |

`strict.yaml` 原本漏了 `step_timeout_s` —— base 变 `null` 后它会跟着变成无上限，
已补齐并要求它把五项全限住（有测试守着）。

### 测试
`tests/unit/test_budget_no_ceiling.py`（10 例）+ budget/config 既有测试更新。**438 全绿**。
两条关键测试做过**非空转验证**：临时禁用修复后确认它们会失败。

### 注意
`tcad/server/app.py` 里原本用 `int(cfg.loop.max_steps_per_turn)` —— 在 `None` 上会 `TypeError`，
且会在「开一个回合」时炸而不是启动时。已抽成 `budget_limits_from_config(cfg)` 并直接测它。

### 本轮修掉的 4 个真缺陷（都是「看起来正常」那一类）
1. **切走的回合仍会写进新会话**（前端时序）。`abort()` 只停网络，**不停 JavaScript**：被抛下的
   `send()` 的帧回调、`catch`、`finally` 全都会继续跑 —— 于是「已离开该会话」的提示出现在你**从没离开**
   的会话里，`clearLive()` 删掉**新回合**的 live 行，`state.abort = null` 把**新回合**的 controller 解掉。
   → 修：回合带**身份对象** `state.turn`，切走时置 `null`，所有回调以 `state.turn === turn` 为前置条件。
   **教训：`abort()` 不等于取消回调**；一个异步流程要能「作废」，必须有一个可比较的身份。
2. **`POST /sessions` 带已存在的 `model_id` 会把零件重置为 v0**。`create()` 不是幂等的，它重写
   `v0.json`，而且响应还是 `ir_version: 0` 像是新模型。`POST /models` 本来就有 409 守着，`/sessions` 漏了。
   → 修：抽出 **`_model_exists()`**（两个端点共用一份事实），已存在则 409 并说明「改用 thread_id 继续」。
3. **会话列表读取失败被渲染成「还没有会话」**。`state.sessionsError` 被赋值却从没被读过。
   读不到 ≠ 没有，这是对「我的东西还在不在」的相反陈述。→ 修：错误分支带原因 + 重试。
4. **回合结束后顶部标题不更新**。刷了侧栏却没刷 header，每个会话的第一个回合之后标题一直是「新会话」。

### 顺手
`switchSession` 原本 `loadView(true)`：每次切换都强制 tessellate + 光栅化。`/render` 的缓存键是
`(version, view, style, size)`，版本来自该模型自己的 IR，**跨会话不可能串图** → 改缓存优先。
`styles.css` 的 `.s-running` 原本是**永远不会生效**的规则 → 接上（`state.busy` 时标记当前会话）。

  `session_db` 只存文本、不存工具调用与结果，直接回灌会让模型只看到自己的旁白（比没有历史更误导）。
  正解是接 `tcad/context/assembler.py`（已存在、未接线）+ 持久化工具轨迹，独立一轮。
- 不做会话重命名/删除/搜索，不做会话内换模型，不做多标签页协调（服务端无 per-thread 回合锁）。

## 追加：对话中打断（用户指令「新增在对话中可以打断对话的功能」）

### 落地物
- `tcad/loop/engine.py` — `LoopEngine(stop_requested=…)`；`_step` 开头检查（步骤边界）；
  `run_turn` 只在谓词为真时把 `CancelledError` 解释成 `ABORTED`；`STOPPED_BY_USER`；记住最后一个 GateReport。
- `tcad/server/app.py` — `ChatRequest.request_id`、`InterruptRequest`、`RunningTurn`、`POST /chat/interrupt`、
  待停止标记（有界 64 / 30s 过期 / 必被消费）、`/chat` 的 id 唯一性与注册销号、流结束后的合成结果兜底。
- `tcad/server/ui/*` — 「停止」按钮（只在运行时出现，`Esc` 同效）、`newRequestId()`、`stopTurn()`（先接口后断连）、
  `aborted` 结论文案、「已打断」状态灯。
- `tests/unit/test_server_interrupt.py`（9 例）、`test_server_ui.py` 的 interrupting 一组（4 例）。
- `tools/probes/interrupt_live.py` + `docs/renders/interrupt.png`。

### 设计（写在 docs/03 的 D7）
谓词说「为什么停」，取消说「怎么停」，**只有谓词为真时 `CancelledError` 才算 ABORTED**——
别的取消（服务端关闭、客户端断开）保持 asyncio 语义。`request_id` 由**客户端在发请求之前**铸造，
所以停止按钮在任何帧回来之前就能指名；服务端把不认识的 id 记成「待停止」，而不是丢掉。

### 实测（离线替身 1.5s/回复，真 FreeCAD worker）
```
1.96s  模型第 1 步 · 3 个工具调用（ir_commit Gate 相关）
2.27s  turn_end state=aborted          ← 第 2 步的模型调用正在飞时打断
2.27s  result   state=aborted steps=2
打断后 0.01s 结束
```
`0.01s` 是关键：替身每次回复 1.5s，不取消在飞请求的话最坏要等到下一次回复——「打断」会变成「等这一步做完」。
同一会话紧接着再发一条消息仍能跑完并给结论，历史 9 条都在。
真实浏览器（agent-browser + 无头 Chromium）：按钮出现 → 点击 → 状态「已打断」、按钮收起、
对话流出现「⏹ 回合已被打断 … 这不是完成」，无控制台报错；第二回合改用 `Esc` 同样成立；
随后再发一条消息回合照常运行。截图 `docs/renders/interrupt.png`（最终代码）。

### 抓出来的两个缺陷
1. **待停止标记没有过期，会停掉一个后来的回合。** 探针跨运行复用 `request_id`，
   上一轮「打空」的停止请求留在表里，下一轮 `/chat` 一注册就被停住：**第一步之前就 ABORTED，屏幕上无从解释**。
   → 修：30s 过期 + 有界 + 无论是否过期都消费；探针改为每次铸新 id。测试守住了。
2. **「停止」不能靠断开连接假装。** `abort()` 只关 SSE，用户看到的是「已离开该会话」——描述了他没做过的事。
   → 修：`turn.stopped` 区分两种 AbortError，正常路径走接口并把结论留在同一条流上。

**教训**：一个「发生在别处、作用在这里」的操作（停止 / 审批 / 取消）必须**指名对象**，
而指名所需的信息必须在**发起之前**就存在。用「当前正在跑的那个」代替指名，在时序变化时一定出错；
用「永不过期」的标记代替过期，一定误伤。

### 测试
**491 全绿**（451 单测 + 40 契约，11.2 秒）。新增 14 例。
6 处机制做了**非空转验证**（依次删掉：步骤边界检查 / 取消转义 / 端点真的停 / 竞态标记 / 注册处的 id 占用守卫 / 按钮显隐，确认对应测试变红后还原）。

### 仍未验证 / 明确不做
- 打断**停不了 worker 里已经在跑的活**（FreeCADCmd 的一次调用会跑完，结果丢弃）——worker 协议无中途取消。
- 打断**不写进会话记录**（与工具调用、Gate 报告同一现状）；刷新后只看到打断前已生成的内容。
- **真机（DeepSeek）上的打断未实测**；离线替身的时序与真模型不同。
