# 03 · 交互界面与模型配置

> `02-架构设计.md` 定的是「内核长什么样」，本文定的是「人怎么用它」。两条施工线：**交互界面**（能看见、能操作）与**模型配置**（能接真模型，比如 DeepSeek）。

## 0. 现状与真实缺口

已经成立的（不重复施工）：

| 能力 | 状态 |
|---|---|
| 内核 | 240 测试全绿；真 FreeCADCmd 端到端跑通；Gate 是唯一成功判据 |
| 驱动方式 | HTTP `/chat`（SSE）+ CLI（`new`/`chat`/`repl`/`approvals`） |
| 已验证的建模 | 操作者即 LLM，四步从空模型建出 80×50×8 底板 + 40×20 通槽，Gate 全绿 |

缺的四件事，全部是本轮要做的：

| # | 缺口 | 证据 |
|---|---|---|
| A | **没有可视反馈** —— 只能 curl 或盯终端，看不到零件长什么样 | `docs/renders/` 里的图是我手跑脚本生成的，不是应用能力 |
| B | **模型运行期不可配** —— `base_url` 在 `build_services()` 时固化，改模型必须重启 | `wiring.py:481` 构造 `OpenAIClient` 后不再有变更入口 |
| C | **没有 provider 概念** —— 接 DeepSeek 要手写 base_url + 塞环境变量 + 猜模型名 | `configs/default.yaml` 的 `llm:` 段只有裸 `base_url`/`model` |
| D | **人看图没有路径** —— `geo_view` 是**模型工具**，受 `_visual_ok`（checkpoint）与 token 预算双重约束 | `tcad/tools/geo_tools.py:45` 直接拒绝非 checkpoint 调用 |

> 缺口 D 值得强调：现在「模型看图」和「人看图」被绑在同一个通道上。但这两件事的成本模型完全不同——模型的每一张图都烧 token，人的每一张图都不该烧。**把它们分开是这一轮最重要的结构决策。**

## 1. 设计决策

### D1 · 热切换：替换 client，不重建 services

engine 在 `run_turn` 时读 `services.llm`。换模型若走「重建整个 services」，代价是重启 `FreeCADCmd`（数秒）+ 丢失进程内状态。

**方案**：`HotSwapLlm` 实现 `LlmClient` Protocol，内部持有可变 `_client`，`configure()` 原地替换。

```
engine ──读──> services.llm  (永远同一个对象)
                     │
                     └─ HotSwapLlm._client ──(configure 时原子替换)──> OpenAIClient
```

**engine 零改动**，切换的原子性由单次属性赋值保证。`services` 本身也不重建，FreeCAD worker 不受影响。

### D2 · API key：三级优先，永不回显

优先级：`settings.json` 显式值 > `provider.api_key_env` 环境变量 > 空。
落盘权限 `0600`；**任何回传给前端的形态都是掩码**（`sk-…3f9a`），前端也拿不到原文。不引入任何密钥管理依赖。

### D3 · provider 预设 + 动态列模型（这条有实证）

DeepSeek 官方文档**两代模型名并存**：

- 中文文档（api-docs.deepseek.com/zh-cn）：`deepseek-v4-flash` / `deepseek-v4-pro` / `deepseek-v4-flash-vision-exp`
- 英文文档：`deepseek-chat` / `deepseek-reasoner`（对应 DeepSeek-V3.2，非思考/思考模式）

结论：**硬编码模型名必然过期**。所以预设只提供 `base_url` / `api_key_env` / **候选列表**，真实可用列表由 `GET /settings/models` 代调 provider 的 `GET /models` 动态取得。UI 的模型下拉框默认填动态结果，取不到时回退候选列表。

`base_url` 用 `https://api.deepseek.com/v1`（官方明确 `/v1` 与 OpenAI 兼容，且与模型版本无关）。

### D4 · 界面：零构建单页应用

项目无 node 工具链，且 worker 侧「只用标准库」是铁律。因此界面用**原生 ES module + fetch**，无打包器、无框架、无依赖，由 FastAPI 静态托管在 `/ui`。改一个文件刷新即见效，不需要构建步骤——这与项目「声明式优先、少依赖」的取向一致。

### D5 · 人的图与模型的图分离

| 通道 | 端点/工具 | 受 checkpoint 约束 | 消耗 token | 用途 |
|---|---|---|---|---|
| 模型的图 | 工具 `geo_view` | 是 | 是（进上下文） | 让模型确认自己画了什么 |
| 人的图 | `GET /models/{id}/render` | **否** | **否** | 让人随时看当前模型 |

人的图这一路走「worker tessellate → supervisor 光栅化 → 缓存进 `artifact_dir` → 返回 PNG」，**不经过 hook 分发、不经过预算**。缓存以 `(ir_version, view, style, w, h)` 为键，重复请求直接命中文件。

### D6 · 观察者回调：让界面看得见模型在干什么

当前 SSE 只透传 hook 事件 + 最终 result。**看不到模型说了什么、调了哪个工具、工具返回了什么**——恰是界面最有价值的部分。

**方案**：engine 增可选构造参数 `observer`，每个 step 结束时推一个结构化事件 `{assistant_text, tool_calls[], tool_results[], gate_report?}`。默认 `None`，对现有 240 个测试与全部语义零影响。这比复用 hook 更准确：hook 是安全拦截点，不该被观测需求污染。

## 4. 风险与未验证项（不遮掩）

| # | 风险 | 影响 | 对策 |
|---|---|---|---|
| 1 | **DeepSeek 的 function calling 兼容度未实测**，尤其 `thinking` 与 `tools` 同时开启 | 可能工具调用格式异常 | M4 实测；若冲突，provider 预设里关掉 thinking |
| 2 | **环境代理可能劫持对 `api.deepseek.com` 的直连**（本机 `HTTPS_PROXY` 存在且曾 502） | 请求全部失败，且错误信息指向代理而非模型 | provider 预设带 `use_env_proxy: bool`；probe 时显式报告实际使用的代理 |
| 3 | 模型名代际更替（见 D3） | 下拉框里的名字失效 | 动态列模型优先，候选列表兜底 |
| 4 | `context.window_tokens=128000` 仍是估值 | 预算降级阈值不准 | 由 provider 预设补 `context_window`，UI 里可见 |
| 5 | UI 无认证 | 若绑到 `0.0.0.0` 则任何人可用 | 默认只绑 `127.0.0.1`；绑定非回环地址时启动打印警告 |
| 6 | 会话历史写入 `session_db.messages` 尚未确认被 engine 调用 | 刷新后丢对话 | M2 里显式在 server 层记录 user/assistant 消息并写测试 |

## 5. 明确不做

- 不做多用户、权限、登录（单机单用户是当前定位）
- 不做模型自动挑选 / 自动降级（先让人手动选，数据够了再说）
- 不改 worker 的零依赖约束（界面只在 supervisor 侧）
- 不做 3D 交互视口（需要真 GUI 上下文，无头环境下是死路；正交视图已够用）

## B. 端到端实测（离线替身驱动，非真模型）

```
4 步 · state=succeeded · Gate passed=True · blocking=[] · skipped=[wall_thickness]
  ① ir_patch(pad) + commit      → Gate FAIL（缺槽，体积 32000 ≠ 需求 25600）
  ② ir_patch(slot) + commit     → SOLVER 错误：DistanceY([0,1]) 约束冲突（feature_id=sk_slot）
  ③ update_sketch + commit      → Gate FAIL（槽仍未切出）
  ④ update_feature(reversed)    → Gate PASS
  两次失败都被模型看到并修正；wall_thickness 以 advisory 级跳过且如实报告
```

这条轨迹被固化成 `tests/contract/test_chat_end_to_end.py`（14 条断言，跑一次回合约 2.4 秒）。

## C. 被真实路径揪出来的 8 个缺陷

前 5 个是**本轮改动引入或暴露**的，任何一个都不会被"各层单测全绿"发现。

| # | 缺陷 | 为什么没被更早发现 | 后果 |
|---|---|---|---|
| 1 | `rpc.py` 用了未导入的 `E_COMPILE` | `detail.get("kind") or E_COMPILE` 是**短路求值**：错误详情带 `kind` 时不求值。契约测试只走成功路径 | **精确的 solver 错误被替换成 `NameError`** —— 恰好摧毁本项目最看重的能力（可自修复的反馈） |
| 2 | `sqlite_path` 硬编码 `./data/tcad.sqlite3` | 三处调用方各自手工同步它（CLI / driver / 测试），看着像约定 | 覆盖 `data_dir` 后数据库仍指向旧目录：两套配置共用一个库。表现是"测试看到别的测试的数据" |
| 3 | `/settings/llm` 从 Config 反推 provider | Config 里根本没有 provider 概念，反推看起来是合理兜底 | 界面显示 vllm、请求实际发往 custom。**显示与事实不符** |
| 4 | `base_version: "current"` 被拒绝 | 它只是 `agent_driver` 的便利，不在工具契约里 | 最自然的写法换来一条无用的 pydantic 错误，模型无法从中恢复 |
| 5 | `build_client` 接受空 `base_url` | OpenAI SDK 对空 base_url 不报错 | **静默指向 `api.openai.com`**：用户以为在连本地，提示词与 Key 却发去了 OpenAI |
| 6 | UI 里 `$("viewPort")` vs HTML 的 `viewport` | 测试套件看不到浏览器 | 静默返回 null。已加静态一致性测试（id / class / 引用资源） |
| 7 | `SessionDB` 硬绑单线程 | 内核是单线程的，默认值一直成立 | HTTP 服务用线程池跑同步端点，第二个请求即崩 |
| 8 | `ContextConfig.window_tokens` 不随模型变 | `context_window` 有默认值，无法区分"未设置"与"显式设成 128000" | 预算降级阈值按错误的窗口标定 |

**共同的教训**：1、3、4、8 都是"默认值或兜底逻辑让错误看起来像正常"，2、5、6、7 是"两个地方各写一遍同一个事实"。前者靠端到端跑，后者靠"单一事实来源"。

## D. 与计划不符之处

- **计划说要先做界面再做模型配置**，实际先做了配置层。原因：设置面板需要一个可调的接口，先做界面等于写两遍。界面本身一次成型，已含设置抽屉。

# 附录 F · 真机首跑（DeepSeek）

> 第一次用真模型跑，**第一次就抓到一个协议缺口**——而且是离线测试在原理上无法发现的。

## F.1 失败现象

第 2 步（第一次把 assistant 消息连同 tool_calls 回传）被拒：

```
BadRequestError: Error code: 400
  The `reasoning_content` in the thinking mode must be passed back to the API.
```

## F.2 根因

DeepSeek 思考模式返回的 assistant 消息带 `reasoning_content`，**同一轮内**多步循环回放该消息时**必须原样带回**。

而当时：

- `LlmReply` 没有这个字段，`OpenAIClient._parse` 也没解析它——信息在进入系统的第一个环节就丢了；
- `LoopEngine` 构造 assistant 消息时自然也没有它。

**为什么离线测试不可能发现**：`tools/stub_llm.py` 不产生 reasoning（它不是思考模型），而这条要求只存在于真实协议里。这与"成功率路径测试"是同一类盲区——**只有真机能证明真机**。

## F.3 修复

- `LlmReply.reasoning_content`：`_parse` 读 `reasoning_content`（DeepSeek），回退 `reasoning`（部分 OpenAI 兼容服务）；
- `LoopEngine` 构造 assistant 消息时，**有则原样回传**（没有则不加这个键，免得给普通模型塞一个 `null`）。

因为一轮是多步循环，**每步都在回放上一步的 assistant 消息**——所以这个缺陷必然在第 2 步爆，且**任何思考模型都会**。

## F.4 修复后的真机结果

需求「一个 60x40 的安装底板，厚度 10mm」：

```
 1.5s  model  ['ir_get', 'ir_digest']   "I'll start by inspecting the current document state."
 1.5s  tool   ir_get / ir_digest        ok=True
 6.1s  model  ['ir_patch']              "Empty document — I'll create the 60×40 base profile…"
 6.1s  tool   ir_patch   ok=False  [semantic] patch rejected: PatchError: patch produces an invalid IR
 8.7s  model  ['ir_patch']              "The `refs` list is for feature-to-feature dependencies; the …"
 8.7s  tool   ir_patch   ok=True
10.2s  model  ['ir_patch']              "Now let me record the confirmed requirements and commit."
10.2s  tool   ir_patch   ok=True
11.2s  tool   ir_commit ok=True  gate=PASS
11.2s  RESULT state=succeeded steps=5 tokens_in=21741 tokens_out=2568
```

**11 秒、5 步、Gate 全绿**，几何为 60×40×10 的底板（等轴测、比例正确）。

其中第 2 步失败 → 模型**读懂了错误并自行修正**（它自己指出 `refs` 的语义）。这是本项目最核心的假设——**"反馈质量决定能否自修复"**——第一次真机样本就给出了正面证据。

## F.5 这次真机还顺手证实的事

| 假设 | 结果 |
|---|---|
| 工具面可被真模型驱动（不需要我把参数喂进去） | ✅ 模型自己选了 `ir_get` → `ir_patch` → `ir_commit` 的正确顺序 |
| 失败信息可被真模型理解并修复 | ✅ 一次 invalid IR，一次自修复 |
| 思维链与工具调用可以并存 | ✅ 正是靠 F.3 的回传修复 |
| 成本 | 一轮 5 步约 24k 输入 / 2.6k 输出 token |
