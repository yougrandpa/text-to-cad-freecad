## 1. 五个十字路口（架构分叉，我作为架构师的判断 + 需你拍板）

### 分叉 A：形态 —— 自建 harness，还是寄生在现成客户端上？

现状对照（我查过的真实项目）：

| 已有实现 | 形态 | 谁拥有 E 层执行循环 |
|---|---|---|
| `neka-nat/freecad-mcp` | FreeCAD 插件内跑 RPC/MCP，暴露 `execute_code` | Claude Desktop |
| `voitta-ai/voitta-freecad-mcp` | 双进程：MCP server + FreeCAD 内 HTTP bridge（QTimer 主线程队列） | MCP 客户端 |
| `mattackerman1/freecad-tool-server` | 在 FreeCAD 自带 Python 里 in-process import | 任意 MCP/HTTP 客户端 |

**共同点：它们都不造 harness，只造工具层（T 层），把 E/C/S/L/V 全部外包给别人。**

- 选**寄生式**：工作量小，一两天能跑通 demo；但 C/V/S 全在别人手里，你无法做「几何校验器」和「截图回灌」这类 CAD 专属能力，产品差异化等于零。
- 选**自建 harness**：C/S/V/L 全归你，能做 ④⑤；代价是要自己搭执行循环、会话存储、审批门。
- 选**混合**：自建 harness 内核，同时暴露一层协议让外部客户端可嵌（这是 `Codex Harness` 的 app-server 路线——把 harness 做成稳定可嵌入的协议表面）。

> **我的建议：混合，但先内核后协议。**
> 理由：你要的差异点全在 C/V/S，这些必须自己拥有；而「能被别人嵌入」是后期增量，不是第一天的事。

### 分叉 B：生成路径 —— 让模型写自由 Python 脚本，还是产出受控特征树？

这是本项目**风险最集中**的决策。

| 路线 | 能力上限 | 可验证性 | 可编辑性 | 安全 |
|---|---|---|---|---|
| B1 自由 Python 脚本（`execute_code`） | 最高，能碰 FreeCAD 全 API | 极差：脚本里能写 `os.remove`，也能写错几何 | 差：改一次要重写脚本 | 差，需沙箱 |
| B2 受控 DSL / 特征树（JSON/YAML → 编译器 → FreeCAD API） | 中高，覆盖 PartDesign 常用特征 | 好：结构可静态校验 | 好：能定位到第 N 个特征改参数 | 好 |
| B3 混合：声明式特征树为主 + 逃生舱脚本 | 高 | 中高（逃生舱单独走审批） | 好 | 中 |

> **我的建议：B3。** 主路径走 B2（可校验、可增量改、可审计），把 B1 作为**显式审批后才解锁的逃生舱**。
> 依据：`Claude Code` 的 hooks 是「确定性拦截」的产品化范本——高危动作必须过确定性门，不能只靠提示词劝；`Codex Harness` 也是把高危操作挂 HITL approval 暂停等授权。
> 纯 B1 会让你的 ④ 层形同虚设：一段黑盒脚本跑完，你只有最终 BRep，没法做「特征级」校验。
> **→ 你的选择：** ______

### 分叉 C：多轮编辑的真相源（S 层）—— 谁是唯一真相？

聊天式 CAD 最真实的日常不是「从零建一个」，而是「**把那个孔往右挪 5mm**」。

- C1：真相源 = FreeCAD document 本身（`.FCStd`）→ 指代消解难，历史是黑盒
- C2：真相源 = 生成的脚本 → 改一次重跑全脚本，副作用不可控
- C3：真相源 = **自有中间表示（IR）：特征 DAG + 参数表 + 命名**，FreeCAD document 只是它的投影产物

选 C3 后，模型改的是 IR 里的一个参数，重放得到新模型；同时能让模型看到「特征树摘要」而不是整份 BRep——**这是解决上下文爆炸的关键**。

> **我的建议：C3（IR 为真相源）。**
> 依据：`event-sourcing` 模式——只追加不修改，事件流是单一真相源；`pure-function-effects`——把「改参数 → 重放建模」做成可复现的纯过程。这两条迁移到 CAD 正好：IR 是真相，模型是投影。
> **→ 你的选择：** ______

### 分叉 D：视觉反馈 —— 要不要上多模态截图闭环？

FreeCAD 可以离屏渲染多视图（`voitta-ai` 那个项目已证明能返回 flat_lines / hidden_line / wireframe 多风格截图）。

- 不上：模型纯靠文本规格建模，**闭眼画图**，几何错了它自己不知道。
- 上：每一步渲染 2–4 张标准视图回灌给多模态模型，**睁眼画图**。

> **我的建议：必上。** 这是 CAD 相对文本任务最大的架构增量，也是你 ⑤ 层存在的理由。
> 代价要说清楚：多模态输入 token 极贵，必须配「截图缓存 + 只在关键节点渲染 + 低分辨率降采样」的成本策略。
> **→ 你的选择：** ______

### 分叉 E：参数化程度 —— 每次重生成，还是增量改特征？

- E1 每次从零重生成：简单，但用户改一个尺寸会丢掉其它手工调整
- E2 增量改 IR 节点 + 重放：需要 IR 稳定、特征命名可靠，但体验是真正的「对话式改图」

> **我的建议：E2。** 这是聊天式 CAD 与「一次性生成器」的分界线。

## 3. 你在回答前可以先看这两个「反例」（我主动构造的，逼方案更健壮）

1. **「改一下那个孔」指代失效**：如果 IR 里的特征没有稳定命名，第二轮对话里「那个孔」就无法消解到节点 → 必须有「特征命名 + 几何语义摘要」进上下文的设计，否则多轮编辑一开始就废。
2. **校验通过但产品不可用**：几何校验全过（水密、体积对、STEP 可往返），但模型**不符合工程常识**（壁厚 0.2mm、孔径小于刀具直径、悬空特征无法加工）。→ ④ 层只能保证「几何自洽」，保证不了「工程合理」。这部分必须诚实标为未知区，靠人工抽查或领域规则库兜底，**不要假装能自动评分**。
